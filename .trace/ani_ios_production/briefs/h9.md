# Helper brief H9 — P5 groundwork: the layout bench harness and the P2 scenes

You are helper H9 on the ani layout engine. You build the bench harness of §11.5 and the scenes of
§11.6 that need only P2. Other helpers are changing the engine at the same time. You do not touch
engine code: a failing metric is evidence for the iteration log, not something you fix. The
orchestrator reviews every line and runs the deciding measurement. The Chief Justice judges the
P5 checkpoint.

## Setup

- Work in your own git worktree. First run `git reset --hard 776915f`; worktrees can start from a
  stale base.
- Install with `pnpm install --frozen-lockfile --offline` if `node_modules` is missing.
- Build with `npx tsup` in `packages/core`, `packages/layout` and `packages/react`, in that order.
- Browsers: export `PLAYWRIGHT_BROWSERS_PATH=/home/user/.pw-extra` on every browser command.
  Chromium headless shell 1187, WebKit 2203 and Firefox 1490 are installed.
- Biome: pass `--vcs-use-ignore-file=false`.
- Never read anything from a directory named `ui-kit`. Never use sudo. Kill processes by PID only.

In `packages/layout/ARCHITECTURE.md`, read these word by word:

## Prerequisite 2 — essential purpose

"Snap, never wrong motion", proven frame by frame. The harness is the judge of iOS-native grade:
- its oracle shares no code with the solver or `physics`;
- its gates come from §11.6 verbatim;
- no tolerance is chosen by you, and a scene never passes by construction.

A harness that cannot fail is worthless. For every metric, show a deliberately broken input that
makes it fail.

The top-level owner has explicitly ruled that this harness and these scenes are the product-like
proof surface for ani. Do **not** replace them with, or expand them into, a generic canvas,
whiteboard, diagram editor or other standalone application. Production realism belongs inside the
bounded interaction scenes and their frame evidence.

## Prerequisite 3 — task boundary

### Thesis: what you build

1. **`bench/layout/`**, a TypeScript runner in the repo's style: Node with native type stripping,
   Playwright, request interception, no ports.
   - The page is cross-origin isolated (COOP `same-origin`, COEP `require-corp`).
   - Options: `--engine chromium|webkit|firefox`, `--scene <glob>`, `--runs` (default: 1 warm-up
     plus 5 measured, each in a fresh browser process), `--out <file>`, `--compare <file>`.
   - Commands: `pnpm bench:layout` and `pnpm bench:layout --check`. `--check` exits 1 when any
     gate fails, after writing the report.
2. **The fingerprint** of §11.5, recorded exactly. A report is `pinned` only when every item
   matches the table, otherwise `advisory`. Record the 1-minute load at start.
3. **The independent oracle.** Closed-form timing curves and an independent spring integrator.
   - The spring may be a high-order numerical integration of the ODE, not the analytic solution
     of `physics`.
   - Each scene's script states its expected tracks.
   - Unit-test the oracle against hand-computed values.
4. **Frame scoring.** Every metric of §11.6, per frame and per participant, on the manual clock.
   Report the worst value, its frame and its participant.
5. **The real clock.** Per §11.5:
   - granularity `g`, and samples of one frame, or the mean of 20 frames when `g > 0.05 ms`;
   - nearest-rank percentiles;
   - the per-run statistics of the §11.5 table, and the median of the 5 runs.

   The commit gate, steady-frame p95, sustained commits and held frame are computed and reported
   with their budgets. The held-frame and sustained-commit shapes that need the drive seam are
   reported as `pending: P4`.
6. **Scenes.** Every §11.6 scene marked P2: S-CARD, S-PHOTO, S-SEG, S-ACC (R), S-STACK, S-ISLAND,
   S-INSERT (R), S-DELETE (R) and S-BULK. Each is a self-contained page module.
   - Build them with the quality of a real iOS reproduction: realistic geometry, typography,
     radius and spring parameters taken from the iOS feel (state the parameters).
   - Each scene is also viewable as a page, so a person can watch it.
   - S-REORDER and S-SHEET are stubs reported as `pending: P4`.
7. **Iteration 0.**
   - Run the full set in Chromium and WebKit, and Firefox as advisory.
   - Write `bench/layout/ITERATIONS.md` with the first iteration: every failing metric, with its
     worst frame and a root-cause hypothesis from the evidence. Do not fix the engine.
   - Commit the report JSON under `bench/layout/results/`.
8. **Negative controls.** A test per metric that feeds a deliberately broken trace (a 0.1 px
   offset, a velocity jump, a leftover declaration, a wrong status) and shows the metric fails.

### Antithesis: what you must not do

- Do not edit `packages/*/src`, `tests/browser/` cases or `ARCHITECTURE.md`.
- Do not build a generic canvas/editor framework or unrelated product application as a proxy for
  native-grade proof.
- Do not change a gate value or invent one. Where §11.6 is silent or ambiguous, report the
  sentence and take the strictest reading.
- No placeholder scene that skips scoring. No `pending` except S-REORDER, S-SHEET and the
  shapes that need the drive seam.
- Do not push, and do not touch any remote. Commit in your worktree with plain messages and no
  model names.
- Another helper runs browser tests at the same time. Iteration 0's cost numbers are therefore
  advisory: mark the load in the report. The orchestrator takes the deciding measurement.

### Synthesis: done means

- Unit tests for the oracle, the scoring and the statistics, plus the negative controls, all pass.
  `pnpm ts:typecheck` and biome (0 errors) are clean.
- `pnpm bench:layout --check` runs end to end in Chromium and WebKit and writes a report.
- `ITERATIONS.md` holds iteration 0.
- Final reply:
  - worktree path, branch and commit hashes;
  - files;
  - the scene table with each metric's worst value per engine;
  - every ambiguity;
  - each deviation with its reason.
